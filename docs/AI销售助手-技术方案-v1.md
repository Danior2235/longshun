# AI 销售助手技术方案 v1.0

> 技术栈主线：**WorkBuddy（Agent 工作台） + 微信小程序（销售端） + 企微/微信对话导入 + 电话录音导入**
> 适用主体：酒店 / 餐饮 / 会议 多业态集团
> 版本日期：2026-08-09　　状态：初稿，供周一汇报使用

---

## 0. 一句话讲清楚

> 把销售经理**每天真实发生的两件事**——微信聊天、打电话——变成结构化数据，喂给一个懂酒店业务、懂房态成本、懂历史案例的 AI，让它当"销售总监"，实时告诉一线：**这个客户要什么、下一步该做什么、方案和报价长什么样。**

不做"又一个 CRM"。CRM 是等人填的，这套东西是**自动长出来的**。

---

## 1. 为什么是这四件套

| 组件 | 定位 | 不可替代的理由 |
|---|---|---|
| **WorkBuddy** | Agent 运行时 + 能力孵化器 | 已有 Skills / MCP / Automations 体系，能直接跑爬虫、连业务系统、跑长任务。**Demo 阶段零开发即可演示**，验证过的能力再沉淀为线上服务 |
| **微信小程序** | 一线销售的手机入口 | 销售不装 App。小程序是唯一"打开即用"的载体；且能通过 `chooseMessageFile` 从微信聊天里直接取素材 |
| **微信对话导入** | 客户意图的第一现场 | 80% 的客户需求首次表达发生在微信，不是电话也不是邮件 |
| **电话录音导入** | 决策与异议的第一现场 | 关键的价格拉锯、异议、承诺，几乎只在电话里发生。这是 CRM 永远抓不到的 |

### 1.1 WorkBuddy 的双轨定位（重要，汇报时必讲）

WorkBuddy 是**桌面端 Agent 工作台**，不适合直接扛小程序的线上并发。所以架构上走双轨：

```
轨道 A（内部孵化 / 立刻可用）
  技术负责人 + 销售总监 在 WorkBuddy 里
  → 写 Skill（销售 SOP）、连 MCP（房态/CRM/案例库）、配 Automation（每日爬招标）
  → 当天就能出效果，用于 Demo 和内部重度用户

轨道 B（线上服务 / 逐步沉淀）
  把 A 里验证过的 Prompt / Skill / 工具链
  → 迁移为 Agent 服务（Python/Node + LLM API）
  → 小程序、看板、企微机器人 都调这个服务
```

**价值主张**：不用"先做半年平台再看效果"。轨道 A 一周出东西，轨道 B 用真实反馈驱动，避免建了个没人用的系统。

## 3. 通道一：微信对话导入（最关键，也最容易踩坑）

### 3.1 先说结论：三条路，只有一条是主路

| 路径 | 合规性 | 覆盖率 | 是否推荐 |
|---|---|---|---|
| **A. 企业微信会话存档 API** | ✅ 官方合规 | 只覆盖企微对外聊天 | ⭐ **主路** |
| **B. 小程序内导入（文件/截图 OCR/粘贴）** | ✅ 员工主动上传 | 覆盖个人微信 | ⭐ **补充路，Demo 主力** |
| **C. 破解个人微信本地数据库** | ❌ 违反微信条款，有法律风险 | 全覆盖 | 🚫 **不做** |

> **必须向老板说明的一点**：个人微信的聊天记录，**没有任何合法接口可以自动读取**。要拿到，公司必须推动销售侧从"个人微信加客户"迁移到"企业微信加客户"。这是**业务决策，不是技术问题**。技术上我们把 B 路径做顺手，作为过渡。

### 3.2 主路：企业微信会话存档

**前置条件（需老板拍板）**
- 企业微信管理后台开通「会话内容存档」增值服务，按人授权，约 **90 元/人/年**
- 员工侧需同意；外部客户首次会话时企微会自动提示"该企业已开启会话存档"（合规告知由微信官方完成，我们不用背这个责任）

**技术链路**

```
企微服务端
  │  ① 拉取：WeWorkFinanceSdk.GetChatData(seq, limit=1000)
  ↓     返回加密消息数组，含 encrypt_random_key + encrypt_chat_msg
采集服务 (Python/Go 常驻进程，5 秒轮询)
  │  ② 解密：RSA 私钥解出 AES key → DecryptData() → 明文 JSON
  │  ③ 媒体：GetMediaData() 分片拉取语音/图片/文件 → 上传 COS
  ↓  ④ 语音消息(amr) → 转码 wav → 走 ASR，和电话录音同一条流水线
消息标准化层
  │  ⑤ 统一映射为内部 Message 模型（见 3.4）
  ↓  ⑥ 写入 raw_message 表 + 投递 Kafka/MQ 供下游消费
```

**关键实现要点**

- SDK：`libWeWorkFinanceSdk`（官方 C 库），生产用 Go/Python 封装；**注意它不是纯 HTTP API，需要在 Linux 上加载 .so**
- `seq` 是全局递增游标，必须**持久化到 DB**，进程重启从上次 seq 继续，不能从 0 重拉（会重复且慢）
- 单次拉取上限 1000 条，返回条数 = limit 时应立即再拉一次（追赶模式），否则 5 秒退避
- 消息类型需覆盖：`text / image / voice / video / file / link / weapp / chatrecord(合并转发) / revoke(撤回) / agree(同意存档)`
- **撤回消息要保留**——销售撤回的报价、客户撤回的吐槽，往往是高价值信号
- 私钥管理：企微公钥加密，私钥存 KMS / Vault，**绝不入代码库**

### 3.3 补充路：小程序内导入（Demo 阶段主力）

三种输入方式，都在小程序「导入客户对话」页面：

**① 从聊天中选文件** — `wx.chooseMessageFile`
- 微信官方 API，可从会话里选 txt / 图片 / 文档
- 销售把客户发的需求文档、报价单直接选进来
- 限制：只能选**当前会话里已有的文件**，不能选聊天记录本身

**② 聊天截图 OCR + 气泡方位判断说话人**（这是个巧思）
```
截图上传 → 腾讯云 OCR 通用印刷体(带坐标 Polygon)
  → 按 y 排序还原时序
  → 按气泡 x 中心位置分左右：
       x_center < 屏宽 × 0.45  → 客户（左侧气泡）
       x_center > 屏宽 × 0.55  → 销售（右侧绿色气泡）
  → 过滤时间戳行、系统提示行
  → 输出带 speaker 标注的对话序列
```
- 实测准确率：单人对话截图 90%+；群聊需额外识别昵称行
- 补强：对绿色气泡做**色值检测**（微信绿 #95EC69）辅助判定，准确率可到 95%+

**③ 直接粘贴文本** — 销售长按复制聊天内容粘贴，LLM 做说话人切分。兜底方案，永远可用。

### 3.4 统一消息模型

不管来自企微、OCR 还是录音，全部归一化：

```json
{
  "msg_id": "uuid",
  "source": "wecom | ocr | asr | manual",
  "conversation_id": "会话/客户维度聚合键",
  "customer_id": 10086,
  "sales_user_id": "zhangsan",
  "speaker_role": "sales | customer | unknown",
  "speaker_name": "张三",
  "content_type": "text | image | voice | file",
  "content": "宴会厅 8 月 20 号能排 30 桌吗",
  "media_url": "cos://.../xxx.wav",
  "sent_at": "2026-08-09T14:23:11+08:00",
  "confidence": 0.93,
  "raw": { }
}
```

**这一层是整个方案的地基**——上游有 5 种来源，下游有 N 个 Agent，中间必须只有一种数据形态。

## 4. 通道二：电话录音导入

### 4.1 三种获取方式，按推荐度排序

| 方案 | 怎么拿到录音 | 优点 | 缺点 |
|---|---|---|---|
| **① AXB 中间号（强烈推荐）** | 销售通过小程序点击拨号，走云通信隐私号，平台侧自动录音落 COS | 自动化程度最高、客户号码脱敏、录音质量稳定、有官方告知音 | 需接入云通信，约 0.1 元/分钟 |
| **② 云呼叫中心** | 前台/预订中心座机走 TCCC，录音自动归档 + Webhook 通知 | 覆盖来电（inbound）场景 | 只覆盖坐席，覆盖不到外勤销售 |
| **③ 手机本地录音上传** | 安卓通话录音文件 → 小程序批量上传 | 零改造，Demo 立刻能用 | iPhone 不支持；依赖销售自觉；文件杂乱 |

> **落地建议**：Demo 用 ③；MVP 上 ①（外呼）+ ②（来电），③ 作为长期兜底。

### 4.2 录音处理流水线

```
录音文件 (mp3/wav/amr/silk)
   │ ① 上传：小程序 → 后端签发 COS 临时密钥(STS) → 客户端直传，大文件分片
   ↓   （不走后端中转，省带宽、避超时）
   │ ② 预处理：ffmpeg 统一转 16k/8k 单声道 wav，去静音，音量归一
   ↓
   │ ③ ASR：腾讯云「录音文件识别」CreateRecTask
   ↓     EngineModelType = 8k_zh_large（电话场景专用模型）
   │     SpeakerDiarization = 1, SpeakerNumber = 2  ← 说话人分离
   │     HotwordId = xxx  ← 挂载酒店业务热词表（关键，见下）
   │     FilterDirty / FilterModal = 0（保留语气词，用于情绪判断）
   ↓ ④ 轮询 DescribeTaskStatus → 拿到带时间戳、带 speaker 标签的文本
   │
   │ ⑤ 角色归属：ASR 只给 speaker_0 / speaker_1，需判断谁是销售
   ↓     启发式：① 说"您好，这边是XX酒店"的是销售
   │              ② 总说话时长更长的通常是销售
   │              ③ 声纹注册（长期方案，销售录 30 秒底库）
   │
   │ ⑥ LLM 结构化抽取（见 4.4）
   ↓ ⑦ 落库 + 触发下游 Agent（更新画像、生成待办、预警）
```

### 4.3 热词表 —— 决定 ASR 好不好用的关键

通用 ASR 听不懂酒店行话，必须建热词表（腾讯云支持 128 个热词，权重 1-11）：

```
宴会厅 10 | 会议室 10 | 房态 11 | 早鸟价 10 | 协议价 11 | 挂账 10
自助餐 9 | 围餐 10 | 圆桌 9 | 桌数 10 | 主桌 9 | 茶歇 10 | 场地费 11
标间 9 | 大床房 9 | 套房 9 | 加床 9 | 含双早 11 | 免费升级 9
团建 10 | 年会 11 | 婚宴 11 | 答谢会 10 | 政采 10 | 招投标 10
```

> 上线前用 50 通真实录音做一轮**词错率(WER)基线测试**，热词优化前后对比，这个数据在汇报时很有说服力。

### 4.4 LLM 结构化抽取 Schema

对话（微信/电话统一）→ 结构化商机信息：

```json
{
  "customer": { "company": "XX科技", "contact": "李经理", "role": "行政总监", "phone_masked": "138****5678" },
  "demand": {
    "biz_type": ["会议", "客房", "餐饮"],
    "event_date": "2026-09-15 ~ 2026-09-16",
    "headcount": 120,
    "room_nights": 60,
    "meal_rounds": 3,
    "venue_requirement": "需要 150 人剧院式会场 + 2 个分会场",
    "budget_hint": "客户提到人均 300 以内",
    "budget_confidence": 0.7
  },
  "signals": {
    "intent_score": 0.82,
    "stage": "需求确认 | 方案比价 | 临门一脚 | 已流失",
    "objections": ["觉得场地费偏高", "担心停车位不够"],
    "competitors": ["隔壁 XX 国际"],
    "risk_flags": ["客户提到还在比价", "决策人未出面"],
    "emotion": "偏正面，但对价格敏感"

## 5. 小程序端设计

### 5.1 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | 微信小程序原生 + **TDesign WeApp** | 腾讯系组件库，与后续企微侧边栏复用度高；不引入 Taro 的构建复杂度 |
| 登录 | `wx.login` → code2session → openid，与企微 userid 绑定 | 同主体下可用 unionid 打通企微与小程序身份 |
| 文件上传 | STS 临时密钥 → **客户端直传 COS** | 录音文件动辄几十 MB，绝不走后端中转 |
| 实时推送 | 订阅消息 + WebSocket（前台时） | AI 分析完成、商机预警走订阅消息 |
| AI 对话 | SSE 流式（小程序需用 `wx.request` enableChunked） | 打字机效果，体验关键 |

### 5.2 核心页面（6 个，够 MVP 了）

1. **今日作战台** — AI 生成的当日待办：该跟进谁、说什么、附什么材料
2. **客户档案** — 自动生成的画像 + 全渠道对话时间轴（微信/电话混排）
3. **导入中心** — 录音上传 / 截图 OCR / 文件导入 / 文本粘贴
4. **AI 问答** — "帮我给这个客户出个 120 人会议 + 60 间房的报价"，直接出方案
5. **方案库** — 生成的方案/报价，可一键转发到微信给客户
6. **我的业绩** — 个人商机漏斗、转化率、AI 建议采纳率

> 管理层的实时数据看板走 **Web 端**，不塞进小程序——屏幕太小，图表体验差。

## 6. WorkBuddy 侧的具体落地

### 6.1 要建的 Skills

| Skill | 干什么 | 触发方式 |
|---|---|---|
| `conversation-insight` | 输入对话文本 → 输出 4.4 的结构化 JSON | 每条新对话自动触发 |
| `proposal-generator` | 需求 + 房态 + 成本 + 历史案例 → 报价方案 Word/PDF | 销售主动调用 |
| `lead-hunter` | 爬招标网/政企动态/新闻 → 输出线索卡片（见第 14 章 crawler 模块，仓库 `D:\Source\Repos\lszy_yx\crawler`） | Automation 每日 08:00 |
| `daily-briefing` | 汇总昨日商机变化 → 生成总监晨报 | Automation 每日 08:30 |
| `invoice-advisor` | 客户信息 + 合同类型 → 建议用哪个营业执照签约 | 销售主动调用 |

### 6.2 要建的 MCP Server（自建）

| MCP | 暴露的工具 | 对接后端 |
|---|---|---|
| `hotel-pms-mcp` | `query_room_availability` / `query_rate` / `hold_room` | PMS（西软/绿云/Opera） |
| `venue-mcp` | `query_venue_availability` / `query_venue_price` | 会议宴会预订系统 |
| `cost-mcp` | `get_cost_baseline` / `check_margin` | 财务系统 |
| `case-library-mcp` | `search_similar_cases`（向量检索） | pgvector 案例库 |
| `crm-mcp` | `get_customer` / `update_opportunity` / `create_task` | 自建客户中心 |

> **`check_margin` 这个工具很关键**：AI 出报价前必须查毛利红线，低于阈值自动标黄并要求总监审批。这是让老板放心把报价权交给 AI 的前提。

### 6.3 Automations（定时任务）

```

## 7. 数据整合与业务协同

### 7.1 业务系统接入方式（按优先级）

1. **开放 API** — 最优。绿云、西软新版本都有 OpenAPI
2. **只读从库 + CDC** — 次优。Debezium/Canal 监听 binlog，准实时同步。**要求 DBA 开只读账号**
3. **定时导出文件** — 兜底。老旧系统只能这样，T+1 精度

### 7.2 数据分层

```
ODS  原始层   各系统原样落地，不做加工，保留全量历史
DWD  明细层   清洗 + 统一维度（客户 ID、日期、门店、业态四个主维）
DWS  汇总层   按天/按业态/按渠道预聚合，看板直接查这层
ADS  应用层   面向具体看板/AI 的宽表
```

**客户主数据（MDM）是难点**：同一个客户在 PMS 叫"XX科技有限公司"，在餐饮 POS 叫"XX科技"，在会议系统是手机号。需要建**客户 ID-Mapping 服务**，用「统一社会信用代码 > 手机号 > 公司名模糊匹配 + 人工确认」三级策略打通。

### 7.3 跨业态协同（对应需求 2.2）

```
客户在微信说："9月中旬 120 人年会，要住 2 晚"
  ↓ conversation-insight 抽取出三条业务需求
  ↓ 协同引擎自动拆单
  ├→ 客房部：查 9/15-9/16 60 间房房态 → 生成预留任务
  ├→ 会议部：查 150 人会场 → 生成场地锁定任务
  └→ 餐饮部：查 12 桌宴会承接能力 → 生成菜单方案任务
  ↓ 三方回填 → 汇总为一份整体方案 → 推回销售经理
  ↓ 全流程留痕，谁在哪一步卡了多久，一目了然（对应需求 2.3 问题追溯）
```

## 9. 安全与合规（必须写进汇报，这是老板会问的）

| 风险点 | 措施 |
|---|---|
| **通话录音合法性** | ① 外呼走 AXB 中间号，平台自带告知音"本次通话可能被录音" ② 来电 IVR 前置提示 ③ 手机录音需员工签署授权书 |
| **微信会话存档** | 只做企微官方存档，客户端有官方合规提示。**明确不碰个人微信数据库** |
| **个人信息保护法** | 客户手机号/身份证在库内加密存储，展示层脱敏；录音 COS 设置 180 天生命周期，到期转归档/删除 |
| **数据权限** | 销售只看自己客户；总监看团队；财务数据（成本/毛利）单独权限位 |
| **AI 幻觉风险** | ① 报价必须走 `check_margin` 校验 ② 房态/价格必须实时查 PMS，禁止模型自己编 ③ 对外文档必须人工确认后发送 |
| **Agent 对外动作** | 发消息、发邮件、锁房等**对外/写操作一律二次确认**，只读操作可自动执行 |
| **密钥管理** | 企微私钥、云 API 密钥统一进 KMS，代码库零明文 |

## 14. 外部线索自动获取：每日招标 / 会议承办信息采集

对应需求 1.1（客户线索获取）。这是投入最小、见效最快、且完全合规的模块——政府/国企/大型企业的会议、住宿、培训、接待类采购，几乎全部通过公开招标发布，是我们这种多业态集团最精准的获客金矿。

### 14.1 为什么从招标网切入
- 招标公告 = 已经明确、有预算、近期要落地的会议/住宿/活动需求，比冷拨电话精准得多。
- 全部公开，无需授权，合规零风险。
- 结构化程度高（采购人、预算、日期、联系方式齐全），AI 可直接转成线索卡片推给对应销售。

### 14.2 模块在整体架构中的位置
```
数据采集层 ⑤ 外部爬虫（每日招标 / 会议承办）
  sources.yaml（可配置信息源 + 关键词，员工维护）
    → fetcher（UA 伪装 / 重试退避 / 编码修正）
    → parser（ccgp 已内置；新增站点用 generic + CSS 选择器配置）
    → matcher（命中业务关键词即相关；命中排除词丢弃）
    → storage（去重 + leads.jsonl / leads_YYYYMMDD.json / leads.csv）
    → 线索卡片 → lead-hunter Skill → 小程序「线索」页 + 企微推送
```

### 14.3 可配置信息源（员工维护，免改代码）
新增一个网站 = 在 `config/sources.yaml` 的 `sources` 下加一段即可。已内置：
- **中国政府采购网（ccgp.gov.cn）**：按关键词（会议服务 / 会议承办 / 住宿服务 / 培训场地 / 接待服务 / 年会 / 宴会 / 活动服务）逐词检索，内置专用解析器。
- **中国招标投标公共服务平台**：通用解析器模板（需按实际页面微调选择器后启用）。
- **各省市公共资源交易中心**：每个城市一个 URL，通用解析器 + 自定义 CSS 选择器即可。

> 不要碰需登录的付费招标网（采招网 / 千里马），合规与成本都不划算；公共资源交易中心的免费公开板块足够覆盖。

### 14.4 相关性匹配逻辑
`matcher` 配置两组词：
- `must_include_any`：命中「会议 / 住宿 / 培训 / 接待 / 年会 / 宴会 / 场地 / 承办」等任一即视为相关，命中越多相关性分越高（0.4 起步，每命中一个 +0.2，封顶 1.0）。
- `exclude`：含「设备采购 / 服务器 / 软件 / 硬件 / 运维 / 系统集成」等直接丢弃（非我方业务）。
- `min_relevance`：低于阈值丢弃（默认 0.5）。

### 14.5 每日运行方式（双轨）
- **轨道 A（立刻可用）**：在 WorkBuddy 配置 `lead-hunter` Automation，每日 08:00 运行 `python run_daily.py`，新增线索自动推小程序 + 企微群。
- **轨道 B（线上服务）**：部署为定时任务（cron / K8s CronJob），结果写入业务库 `customer_opportunity` 表，前端读库展示。
